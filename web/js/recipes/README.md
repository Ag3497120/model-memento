# Combine screen integration

`openCombine({ tools, onOpenTool })` opens an accessible modal over the existing
screen. `tools` is the museum catalog; `onOpenTool` receives an existing museum
tool id. No tool is installed or launched by this module.

Expected JSON responses for the reviewer's routes:

- `GET /api/recipes/catalog`: `{ harnesses, providers, mcp, styles }` or
  `{ catalog: { harnesses, providers, mcp, styles, frontends?, roles?, instructionFiles? }, examples? }`.
  Collections may be arrays or records keyed by id. Harness/provider metadata may
  be wrapped in `meta`. Providers contain `models: [{ id, label }]` and `sources`.
  Browser model ids become `provider-id:model-id`, preserving additional colons.
  Optional choice collections contain `{ id, name }` items.
- `POST /api/recipes/recommend { wish }`: `{ recipes: [recipe, ...] }`.
  A raw array or `{ recommendations: [{ recipe }] }` is also accepted.
- `POST /api/recipes/plan { recipe }`: the result of `planRecipe`, directly or
  wrapped in `{ plan }`. The preview requires `workspace`, `files`, `manual`,
  `unsupported`, and `harnesses` (or `argv`).
  Helper entries in `harnesses` use `role: "helper"`, `helperRole`, `harness`,
  and `model`. Their `mcpServer.bridge: true` indicates Model Memento's task
  bridge; `mcpServer.tool` names the `ask_<role>` tool. A non-bridge server
  represents a direct delegating connection. `mcpServer: null` indicates a
  manual handoff, with `manualReason` retained alongside its source URLs.
  The diagram and plan show each helper's handoff from these entries. Missing
  entries or connection metadata keep the wording neutral.
- `POST /api/recipes/apply { recipe, confirm: true }`: success JSON, optionally
  including `workspace`; HTTP failures, `ok: false`, or `error` are failures.
  There is no apply request until a plan is shown, the person selects
  「作業フォルダを作る」, and then selects 「確認したので作成する」.
  Edits invalidate the preview; duplicate confirmations are consumed only once.
- `GET /api/recipes/obtain?tool=<harness-id>`: `{ url: "https://..." }`.
  `{ obtain: { url } }`, `{ homepage }`, and `{ tool: { homepage } }` are also
  accepted. Unknown links stay hidden; URLs must use HTTP(S), without credentials.

404/405/501 or an HTML response means the route is unavailable. Static hosting
uses `web/data/recipes.json`, generated by the recipes-only block in
`scripts/build-web.js`. Example ranking is local word matching, not an AI call.
The static screen explains that planning and folder creation require the app,
and that each helper's handoff method is shown in the app's plan.
Missing catalog ids are visible as unverified and cannot be sent for planning.
No invented instruction style is inserted when the style catalog is absent.

Offline checks:

```sh
node --test web/js/recipes/data.test.js
npm run build:web -- --offline
```

No browser, server, harness, installer, or third-party binary is needed for these
checks. Visual layout and the future server routes still need reviewer verification.
